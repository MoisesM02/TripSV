1. Introducción

Este manual describe la arquitectura, la base de código y los procedimientos técnicos de Trips SV, un sistema de gestión de contenidos (CMS) para la promoción del turismo en El Salvador. Está dirigido a desarrolladores que necesiten mantener, desplegar o ampliar el sistema.

1.1 Descripción del sistema

El sistema reconoce tres niveles de acceso:

RolCapacidades
Visitante anónimoExplora categorías y destinos, busca con filtros y lee calificaciones, reseñas y conversaciones de la comunidad, sin poder publicar.
Usuario registradoTodo lo anterior, más calificar destinos de 1 a 5 estrellas, publicar reseñas, responder a otros usuarios, guardar favoritos y planificar itinerarios de viaje día por día.
AdministradorTodo lo anterior, más la gestión de categorías y destinos (con imagen y contenido enriquecido) y la moderación de comentarios: ocultarlos, volver a mostrarlos o eliminarlos.

2. Arquitectura del sistema

Trips SV sigue el patrón MVC (Modelo–Vista–Controlador) de ASP.NET Core, organizado en capas lógicas (N-capas) dentro de un mismo proyecto web: presentación, negocio y datos. Cada capa solo conoce a la capa inmediatamente inferior a través de interfaces.

2.1 Justificación

  • Renderizado del lado del servidor. Las páginas públicas del catálogo deben cargar rápido y ser indexables. MVC con Razor genera HTML completo en el servidor sin depender de un cliente pesado en JavaScript.
  • Formularios con validación y protección integradas. El sistema es intensivo en formularios (reseñas, calificaciones, administración). MVC ofrece enlace de modelos, validación con DataAnnotations en servidor y cliente, y tokens antifalsificación sin trabajo adicional.
  • Controladores delgados y reglas testeables. Al concentrar la lógica en servicios, las reglas críticas se prueban sin levantar el servidor web (ver sección 12).
  • Separación por rol. El módulo de administración vive en un Área propia con autorización a nivel de clase, lo que evita exponer por error una acción administrativa.
  • Alternativas descartadas. MVVM corresponde a clientes de escritorio o SPA con enlace de datos bidireccional, innecesario aquí. Una arquitectura de microservicios agregaría complejidad operativa (varios despliegues, comunicación entre servicios) desproporcionada para el tamaño del dominio y del equipo.

2.2 Flujo de una solicitud

Ejemplo: un usuario califica un destino.

  1. El navegador envía POST /Puntuaciones/Calificar con el token antifalsificación.
  2. PuntuacionesController exige sesión iniciada ([Authorize]) y valida el token ([ValidateAntiForgeryToken]).
  3. El controlador llama a IPuntuacionesServicio.CalificarAsync, que valida el rango 1–5, crea o actualiza la calificación del usuario y recalcula el promedio del sitio.
  4. El servicio devuelve un Resultado; el controlador guarda el mensaje en TempData y redirige al detalle del sitio (patrón Post/Redirect/Get), evitando reenvíos duplicados al recargar.

6. Acceso a datos y persistencia

6.1 Entity Framework Core Code-First

El esquema se define en C# (entidades y clases de configuración) y se materializa con migraciones. Las tablas y columnas usan nombres en español en formato snake_case mediante Fluent API. Al iniciar, la aplicación ejecuta SembradorDatos, que aplica automáticamente las migraciones pendientes y crea los roles y los usuarios iniciales si no existen. 

dotnet ef migrations add NombreDeLaMigracion --project TripSV --output-dir Datos/Migraciones
dotnet ef database update --project TripSV

6.2 Cadena de conexión segura

La cadena incluida en appsettings.json usa autenticación integrada de Windows (Trusted_Connection=True), por lo que no contiene usuario ni contraseña. Para otros entornos se sobrescribe sin modificar archivos del repositorio:

EntornoMecanismoEjemplo
DesarrolloUser Secrets (fuera del repositorio)dotnet user-secrets set "ConnectionStrings:ConexionTripSV" "Server=...;" --project TripSV
ProducciónVariable de entornoConnectionStrings__ConexionTripSV=Server=...;User Id=...;Password=...;Encrypt=True
TrustServerCertificate=True es adecuado solo para desarrollo local. En producción use un certificado válido en SQL Server y Encrypt=True.

6.3 Uso eficiente de la persistencia

  • Proyecciones sin imágenes. Los listados (inicio, catálogo, categorías, desplegables) seleccionan solo las columnas necesarias; las imágenes se sirven aparte desde /Sitios/Imagen/{id} con caché HTTP de una hora y carga diferida en el navegador.
  • Conteos en la base de datos. El número de destinos por categoría se obtiene en la misma consulta, sin cargar los destinos completos.
  • Índices. Índices únicos que además garantizan las reglas de negocio, e índices en todas las claves foráneas.
  • Valores precalculados. La calificación promedio y el total de calificaciones se guardan en sitios y se recalculan solo cuando cambia una calificación.
  • Consultas sin seguimiento. Los listados usan proyecciones o AsNoTracking, que no generan seguimiento de cambios en el contexto.

6.4 Datos iniciales

TripSV/Datos/Migracion/datos-mysql.sql carga el catálogo de arranque: categorías, destinos con sus imágenes, reseñas y calificaciones. Se ejecuta una sola vez después de crear la base de datos y se detiene si las tablas ya contienen información: 

sqlcmd -S localhost -d TripSV -E -i TripSV/Datos/Migracion/datos-mysql.sql

8. Manejo de errores y excepciones

  • Errores de negocio (datos inválidos, duplicados, permisos): los servicios devuelven un Resultado con un mensaje claro que se muestra al usuario; no se usan excepciones para el flujo normal.
  • Conflictos de base de datos (dos operaciones simultáneas sobre un índice único o una clave foránea): GuardarSinConflictoAsync captura DbUpdateException y devuelve un mensaje amigable en vez de un error 500.
  • Validación de formularios: DataAnnotations en servidor y validación en el navegador con jQuery Validation.
  • Páginas de estado: UseStatusCodePagesWithReExecute muestra páginas propias para 404, 403 y 400.
  • Excepciones no controladas: en producción, UseExceptionHandler muestra una página de error con el código de solicitud para rastrearlo en los registros; en desarrollo se muestra la página detallada de ASP.NET Core.

9. Rendimiento y escalabilidad

9.1 Rendimiento

  • Consultas proyectadas e índices descritos en la sección 6.3.
  • Imágenes con caché HTTP y carga diferida (loading="lazy").
  • Archivos estáticos con caché de 7 días; asp-append-version invalida la caché al cambiar un archivo.
  • Vistas Razor compiladas en la publicación.

9.2 Escalabilidad

  • Aplicación sin estado en el servidor. La autenticación y los mensajes temporales viajan en cookies cifradas, por lo que se pueden ejecutar varias instancias detrás de un balanceador de carga.
  • Al escalar horizontalmente se deben compartir las llaves de Data Protection entre instancias (por ejemplo con PersistKeysToFileSystem en un recurso compartido o un almacenamiento en la nube) para que las cookies sean válidas en todas.
  • Base de datos. SQL Server permite escalar verticalmente o agregar réplicas de lectura; el DbContext por solicitud admite cambiar a AddDbContextPool para reducir el costo de creación de contextos con alto tráfico.
  • Imágenes. Si el catálogo crece mucho, las imágenes pueden trasladarse a un almacenamiento de objetos con CDN sin cambiar las vistas, porque todas se sirven a través de la acción Imagen.

11. Guía de despliegue

11.1 Ejecutable incluido

La carpeta Ejecutable/ contiene TripSV.zip, la aplicación publicada en modo Release para Windows x64, dependiente del runtime. Requiere tener instalado el ASP.NET Core Runtime 10 y acceso a SQL Server. Se descomprime, se ajusta appsettings.json o las variables de entorno y se ejecuta TripSV.exe.

11.2 Generar una publicación

dotnet publish TripSV/TripSV.csproj -c Release -r win-x64 --self-contained false -p:SatelliteResourceLanguages=es -o publicacion

Para Linux se usa -r linux-x64. Con --self-contained true la publicación incluye el runtime y no es necesario instalarlo en el servidor, a cambio de un paquete más grande.

11.3 Configurar y ejecutar

  1. Definir las variables de entorno: 
    ASPNETCORE_ENVIRONMENT=Production
ConnectionStrings__ConexionTripSV=Server=servidor;Database=TripSV;User Id=...;Password=...;Encrypt=True
UsuariosIniciales__Administrador__Password=UnaClaveSegura123
  2. Ejecutar con Kestrel: dotnet TripSV.dll --urls "http://0.0.0.0:5000", idealmente detrás de un proxy inverso con HTTPS.
  3. En IIS: instalar el ASP.NET Core Hosting Bundle, crear un sitio que apunte a la carpeta publicada y configurar el grupo de aplicaciones con "Sin código administrado".
  4. La primera ejecución aplica las migraciones y crea los usuarios iniciales. Después, cargar el catálogo inicial si se desea.

11.4 Lista de verificación para producción

  • Cambiar las contraseñas de los usuarios iniciales.
  • Usar una cadena de conexión con cifrado y un usuario de base de datos con permisos mínimos.
  • Publicar solo sobre HTTPS con un certificado válido.
  • Configurar el almacenamiento compartido de llaves si hay más de una instancia.
  • Programar respaldos de la base de datos.

12. Pruebas automatizadas

14. Cómo extender el sistema

Pasos para agregar un módulo nuevo siguiendo las convenciones del proyecto:

  1. Crear la entidad en Modelos/ con sus DataAnnotations de validación.
  2. Crear su configuración en Datos/Configuraciones/ (tabla, columnas en español, índices y relaciones).
  3. Agregar el DbSet en ContextoTripSV y generar la migración.
  4. Crear la interfaz y el servicio en Servicios/, devolviendo Resultado y guardando con GuardarSinConflictoAsync.
  5. Registrar el servicio en Program.cs.
  6. Crear el controlador con la autorización adecuada y [ValidateAntiForgeryToken] en las acciones POST.
  7. Crear las vistas reutilizando las parciales y clases de estilo existentes.
  8. Agregar pruebas en TripSV.Pruebas para las reglas del servicio.
